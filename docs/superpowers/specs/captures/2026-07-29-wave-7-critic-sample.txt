WHAT THIS RESPONSE PROVES
-------------------------
1. REGIONS RUN OFF THE CANVAS, IN PRODUCTION, FROM A CORRECT-LOOKING MODEL.
   Three of the four issues below name x1 or y1 = 32 on a 32x32 canvas, whose
   last valid coordinate is 31. `Coord` is `z.int().nonnegative()` with no
   upper bound, so these do not fail validation on the low side the way
   spec 6.4's `[-5,-5,3,3]` example does — they fail nothing at all and would
   have been handed to the revise stage as out-of-bounds edits. Clamping on
   the raw JSON is what turns them into the four corner cells the model
   plainly meant. This is the single strongest argument in the wave for
   repairing before validating, and it came from the model unprompted.

2. THE TWO-TIER CONFIDENCE CASE IS NOT HYPOTHETICAL. Every issue arrives at
   `confidence: 0.95` with `suggestConfidence: 0.3` — spec 6.4's valuable
   cell, verbatim: the problem is real, the fix is a guess. With the default
   floors (0.30 / 0.50) `filterIssues` keeps all four issues and empties all
   four `suggest` strings. A filter that dropped them would hand the revise
   stage nothing at all on this sprite.

3. `id` IS NOT UNIQUE. All four issues share the id
   "inconsistent-edge-patterns". `IssueSchema` does not require uniqueness and
   must not start to: a consumer keying a map on `id` would silently lose
   three of these four findings.

4. The critic obeyed "do not repeat the linter" — the four orphan pixels and
   four outline gaps it was told about appear in none of the issue text — and
   it answered in bare JSON with no markdown fence.
