samples rather than a run and a re-run.

HEADLINE
--------
The pipeline works end to end. Both runs reached AWAITING_USER with
outcome "completed", no timeout, no draft failure, no degraded critique, in
119 s and 155 s. This is the first time the whole design has run against real
models, and the state machine, the DSL draft, the gauge loop, the linter, the
critic parse path, the tool surface and both stop conditions all did what the
spec says.

What A12 did and did not prove here, stated exactly: **no single model call in
either run exceeded 30 s**, so the floor was not observed rescuing a call. (An
upper bound, not a direct measurement: `Round.timings` records stage times, and
per-turn revise times come off the event trace — the longest revise turn in run
A was 9.5 s. A draft or critique stage that made one call is that call.) The
closest was a 28.5 s critique STAGE (run B round 1), which under the pre-A12
16x16 deadline of 30 s would have had 1.5 s of margin — and run A's draft stage
took 19.0 s of which roughly 14 s was a cold model load, against 5.1 s for the
same stage in run B with the model already resident. A cold load plus a call of
that length exceeds 30 s, which is precisely the Wave 10 failure A12 was written
from. So: consistent with A12 being necessary, and not independent proof of it.
What the run does prove is the negative the brief asked for — with the floor in
place, a 16x16 no longer dies at 30 s.

The generator is now the strongest stage and the REVISE stage is the weakest.
In both runs the draft produced a near-perfectly symmetric, 4-colour, sensibly
proportioned sprite, and in both runs the first revise pass made it measurably
worse — coverage down, symmetry down, colours down. And in both runs the
agent's own `ReviseSummary.summary` describes work it did not do.

WHAT THE REVISE AGENT ACTUALLY DOES — run B's tool trace
-----------------------------------------------------------------------
Round 1, turn 1 (8 calls in ONE turn):
    fill_row(y=3, x0=5, x1=12, index=".")
    fill_row(y=4, x0=5, x1=12, index=".")
    fill_row(y=5, x0=5, x1=12, index=".")
    place_pixel(6,3,"8")  place_pixel(7,3,"2")  place_pixel(8,3,"2")
    place_pixel(9,3,"2")  place_pixel(10,3,"8")
Turns 2, 3 and 4 repeat that shape on rows 6-8, 9-11 and 13.
Turn 5: done("Removed abstract blocks and replaced them with fox features…")

  The pattern is: ERASE AN 8-WIDE BAND, THEN PUT 5 PIXELS BACK. Four turns of
  that turned a coverage-0.297, symmetry-1.000 sprite into a coverage-0.133
  stack of bars, and the critic scored the result 1 out of 5. The agent is not
  making local corrections to a drawing; it is trying to redraw the sprite
  through a per-cell tool surface and running out of budget part-way. §6.6
  gives it `place_pixel` and `fill_row` on the premise that "the critic has
  named a specific defect and per-cell control is what's wanted" — but the
  critic's round-1 finding was "this is not a fox", which is not a specific
  defect, and the agent answered it by starting over.

Round 2, turns 6-21: single `fill_row` calls of 1-4 cells, one per turn,
slowly rebuilding — and this is the mode that works. 16 turns, 26 net pixel
changes, and the critic went 1 -> 4.

Every tool result VISIBLE IN THE TRACE was `OK:` — no bounds error, no
off-palette rejection, no unknown-tool error. (The instrumentation recorded a
rolling window of the last four `tool` messages per turn, not all of them, so
this covers most but not provably all of the 22 turns.) The tool surface and its
coercion layer behaved well; it is the agent's strategy that is the problem.
Note also turn 7's `fill_row(y=5, x0=1, x1=1, index="2")` — a one-cell
`fill_row`, which is `place_pixel` spelled the long way — and turn 8's
`fill_row(y=6, x0=6, x1=9, index="8")` re-writing 8 over the cells turn 8's own
row had. A no-op write is accepted and reported `OK`, which is a plausible
mechanism for run A's round-2 pass spending 9 turns and changing nothing.

HONEST SUMMARY
-----------------------------------------------------------------------
Works, and is now proven live:
  - `run()` end to end: DRAFTING -> LINTING -> CRITIQUING -> REVISING ->
    AWAITING_USER, two snapshots per revised round, `outcome: "completed"`,
    `finalState: "AWAITING_USER"`, `error: null`. Every §7.1 transition fired in
    the documented order.
  - No timeout in either run, at the size that used to fail every time. See the
    headline for what that does and does not prove about A12.
  - Both roles on one model. No swap stall was observed. The draft stage took
    19.0 s in run A and 5.1 s in run B; the difference is consistent with a cold
    load in A (nothing was resident before it) and is an inference, not a
    measurement — the harness records no load time separately.
  - A10. Draft `repairs` 0 and `repairedRows` [] in both runs: there was no row
    width to get wrong. Neither draft was rejected, so `draftFailures` is empty.
  - A11, indirectly. Draft stage times of ~5 s (B) and ~19 s incl. cold load (A)
    are consistent with ONE batch clearing the gauge bar, which is what the Wave
    6b capture measured directly. The batch count was not recorded here.
  - Both stop conditions: `empty-diff` (A) and `no-high-severity` (B). Neither
    run hit `round-cap` or `maxReviseTurns`, and `hitCap` was false on every
    revise pass.
  - §6.4's floors did not have to reject anything: every issue in both runs came
    back above `confidenceFloor` 0.30 (4 raw -> 4 filtered, twice, in run A).
    Whether `suggestConfidenceFloor` blanked any `suggest` was NOT captured —
    the trace prints the raw report, and run A round 2 issue [3] already carried
    an empty `suggest` from the model.

Does not work, and needs a decision:
  1. REVISE degrades the draft on its first pass, in both runs. It erases and
     redraws rather than correcting, it destroys the symmetry A10 gets for
     free, and it lowers coverage. This is the largest quality lever in the
     system and it currently points the wrong way on round 1.
  2. `ReviseSummary.summary` is unreliable. Run A round 2 claims a full clear
     and redraw having changed zero pixels; run A round 1 claims an orange
     recolour having placed no orange. Anything reading this field as a record
     — the UI, §13's bench, a human reading a session back — is reading
     fiction. The harness already knows the truth (`diffFromPrev`), so the
     summary should be presented beside the diff, never instead of it.
  3. `CritiqueReport.overall` is not usable as a between-round quality signal.
     Run A: 2 -> 4 while every metric fell. Run B: 2 -> 1 -> 4, correct. Same
     model, one prompt apart.
  4. The critic hallucinates regions. Run A round 2 issue [1] describes a tail
     in a region containing no non-transparent cell, at confidence 0.90.
  5. Nothing is seeded. No stage passes `options`, so there is no `temperature`
     and no `seed` anywhere in the harness. These two runs differ in round
     count, stop reason, wall clock and final sprite. §13's bench cannot
     compare two configurations without this, and §6.8's whole argument for
     serializing the config into `SessionHistory` — so that a difference can be
     attributed — is undercut by an unseeded sampler.
  6. The user gate is doing real work, and not as a convenience. In run A the
     best sprite is ROUND 1 and the run's last round is worse; §8's "accept any
     round, not just the last" is what makes run A a usable outcome instead of
     a failed one.

  run({ client: createOllamaClient(), onEvent }, { prompt: "a sitting red fox,
  front facing", size: { w: 16, h: 16 }, paletteId: "pico-8" }, cfg).
  Expect a different trajectory each time — see finding 5.
